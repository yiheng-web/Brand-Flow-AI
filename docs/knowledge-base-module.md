# Brand-Flow 知识库模块业务逻辑与权限配置说明

> 适用对象：前端组、后端组、AI 逻辑组、产品/测试组  
> 文档目的：统一研发组对 Brand-Flow 知识库模块的理解，明确个人、团队、企业三层知识库的业务逻辑、权限模型、数据结构和节点流调用方式。

---

## 1. 模块定位

Brand-Flow 的知识库不只是传统意义上的「文档知识库」或 RAG 检索库，而是一个面向 AI 图文创作流程的 **创作资产系统**。

它的核心作用是：

1. 为 AI 生图提供品牌上下文；
2. 为 Prompt 专家节点提供素材、规则和模板；
3. 为排版与合成节点提供 Logo、标准色、字体规则等视觉资产；
4. 为自我评估节点提供判断标准；
5. 帮助个人、团队、企业沉淀可复用的创作经验。

一句话定义：

> 知识库是 Brand-Flow 中用于存储、管理、检索和调用创作素材、品牌规则、Prompt 模板、案例经验的核心资产模块。

---

## 2. 知识库内容类型

知识库中不应只存储纯文本，应支持多种创作相关内容。

建议第一版 MVP 支持以下 5 类：

| 类型 | 说明 | 节点流用途 |
|---|---|---|
| Logo | 品牌 Logo、团队 Logo、活动 Logo | 排版合成、品牌约束 |
| 图片素材 | 产品图、参考图、背景图、KV 图 | 品牌知识匹配、图像生成参考 |
| 文本资料 | 品牌介绍、产品介绍、活动说明 | 意图理解、Prompt 生成 |
| Prompt 模板 | 用户或团队沉淀的高质量提示词 | Prompt 专家节点复用 |
| 禁用规则 | 禁用风格、禁用元素、版权风险提示 | Prompt 约束、自我评估扣分 |

后续可扩展类型：

| 类型 | 说明 |
|---|---|
| 标准色 | 品牌主色、辅助色、禁用色 |
| 字体规范 | 标题字体、正文字体、字体使用规则 |
| 布局模板 | 小红书封面、海报、电商主图等模板 |
| 优秀案例 | 可复用的优秀生成结果 |
| Bad Case | 失败案例，用于改进 Prompt 和评分规则 |
| 品牌规范文档 | PDF、Markdown、Word 等规范材料 |

## 3. 知识库层级设计

Brand-Flow 同时面向 C 端个人用户和 B 端团队/企业用户，因此知识库需要分为三层：

```text
个人知识库 Personal Knowledge Base
团队知识库 Team Knowledge Base
企业知识库 Enterprise Knowledge Base
```

### 3.1 个人知识库

面向普通 C 端用户。

使用场景：

- 用户保存自己的常用 Prompt；
- 用户上传个人参考图、产品图、风格图；
- 用户沉淀自己的创作偏好；
- 用户在节点流中调用个人知识库辅助生成。

个人知识库特点：

| 特点 | 说明 |
|---|---|
| 私有性 | 默认仅本人可见 |
| 自由度高 | 用户可自由创建、编辑、删除 |
| 数量可限制 | 可根据免费版/付费版设置知识库数量和容量 |
| 适合 C 端 | 不要求复杂权限配置 |

示例：

```text
我的小红书风格库
我的咖啡宣传图库
我的电商海报 Prompt 库
我的摄影参考图库
```

---

### 3.2 团队知识库

面向小团队、部门、项目组、社团、工作室。

使用场景：

- 团队成员共享活动素材；
- 团队统一使用一套 Prompt 模板；
- 团队沉淀项目案例；
- 团队管理员审核素材后入库；
- 成员在团队空间中调用团队知识库生成作品。

团队知识库特点：

| 特点 | 说明 |
|---|---|
| 协作性 | 团队成员共享素材和规则 |
| 需要权限管理 | 不同成员拥有不同管理能力 |
| 可设置审核流 | 成员上传内容可进入待审核状态 |
| 适合项目组 | 每个团队可以维护独立项目资产 |

示例：

```text
瑞幸新品项目组知识库
HelloWorld 社团宣传知识库
电商运营组素材库
短视频封面 Prompt 库
```

---

### 3.3 企业知识库

面向 B 端企业。

使用场景：

- 企业统一维护品牌标准；
- 所有部门共享企业级品牌规则；
- 企业控制 Logo、标准色、禁用规则；
- 团队生成作品时强制遵守企业品牌规范；
- 企业管理员查看不同团队的创作资产和作品。

企业知识库特点：

| 特点 | 说明 |
|---|---|
| 权威性 | 企业知识库是最高级品牌约束 |
| 强管控 | 企业管理员/品牌管理员维护 |
| 可强制调用 | 企业项目生成时默认启用企业知识库 |
| 多团队共享 | 企业下所有团队均可查看和调用 |

示例：

```text
瑞幸咖啡企业品牌规范库
某高校招生宣传规范库
某电商企业官方素材库
```

## 4. 企业、团队、用户关系

建议系统中引入统一概念：**Space 创作空间**。

用户每次创作都处于一个 Space 下，Space 决定当前可见知识库、可用素材、权限规则和作品归属。

```text
User 用户
├── Personal Space 个人空间
│   └── Personal Knowledge Bases
│
└── Enterprise 企业
    ├── Enterprise Knowledge Bases
    ├── Enterprise Members
    ├── Teams
    │   ├── Team A
    │   │   ├── Team Knowledge Bases
    │   │   ├── Team Members
    │   │   └── Team Works
    │   └── Team B
    │       ├── Team Knowledge Bases
    │       ├── Team Members
    │       └── Team Works
    └── Enterprise Works
```

### Space 类型

```ts
type SpaceType = 'personal' | 'team' | 'enterprise';
```

| Space 类型 | 默认可调用知识库 |
|---|---|
| personal | 个人知识库 |
| team | 当前团队知识库 + 所属企业知识库 |
| enterprise | 企业知识库 |

## 5. 知识库调用优先级

在企业/团队场景下，需要明确不同层级知识库的优先级。

建议优先级：

```text
企业规则 > 团队规则 > 个人偏好 > 用户本次输入
```

示例：

如果企业知识库中配置：

```text
禁止使用黑金奢华风格。
```

但用户输入：

```text
帮我做一张黑金高级感海报。
```

系统应提示：

```text
当前需求与企业品牌规范冲突：企业禁用黑金奢华风格。建议改为企业允许的高级清爽风格。
```

该规则尤其适用于 B 端企业管控场景。

## 6. 角色与权限设计

权限模型分为两层：

1. 企业级角色：决定用户在企业范围内能做什么；
2. 团队级角色：决定用户在具体团队内能做什么。

企业角色和团队角色应分开存储。一个用户可以在企业中是普通成员，但在某个团队中是团队管理员。

---

## 7. 企业级角色

建议企业内设置 3 个 MVP 角色：

| 角色 | 说明 |
|---|---|
| 企业管理员 Enterprise Admin | 管理企业信息、成员、团队、企业策略 |
| 品牌管理员 Brand Manager | 管理企业知识库、品牌规则、官方素材 |
| 普通成员 Member | 查看和调用企业知识库，参与创作 |

后续可扩展：

| 角色 | 说明 |
|---|---|
| 企业所有者 Enterprise Owner | 企业创建者，拥有最高权限 |
| 审计员 Auditor | 查看作品和操作日志，不参与创作 |

| 权限项 | 企业管理员 | 品牌管理员 | 普通成员 |

| 邀请企业成员 | ✅ | ❌ | ❌ |
| 移除企业成员 | ✅ | ❌ | ❌ |
| 创建团队 | ✅ | ⚠️ 可配置 | ❌ |
| 删除团队 | ✅ | ❌ | ❌ |
| 管理企业知识库 | ✅ | ✅ | ❌ |
| 上传企业级素材 | ✅ | ✅ | ❌ |
| 编辑企业级素材 | ✅ | ✅ | ❌ |
| 删除企业级素材 | ✅ | ✅ | ❌ |
| 审核企业级素材 | ✅ | ✅ | ❌ |
| 查看企业知识库 | ✅ | ✅ | ✅ |
| 调用企业知识库生成 | ✅ | ✅ | ✅ |
| 设置企业策略 | ✅ | ❌ | ❌ |
| 查看所有团队作品 | ✅ | ⚠️ 可配置 | ❌ |

## 9. 知识库内容状态

知识库中的每条内容都应有状态，避免未审核或废弃内容被 AI 调用。

```ts
type KnowledgeItemStatus =
  | 'draft'
  | 'pending_review'
  | 'active'
  | 'rejected'
  | 'archived';
```

| 状态 | 说明 | 是否可被节点流调用 |
|---|---|---|
| draft | 草稿，仅创建者可见 | ❌ |
| pending_review | 待审核 | ❌ |
| active | 已生效 | ✅ |
| rejected | 审核不通过 | ❌ |
| archived | 已归档 | 默认不调用 |

## 10. 知识库内容可见范围

```ts
type Visibility = 'private' | 'team' | 'enterprise' | 'public';
```

| 可见范围 | 说明 |
|---|---|
| private | 仅创建者本人可见 |
| team | 所属团队成员可见 |
| enterprise | 所属企业成员可见 |
| public | 平台公开素材，后续扩展 |

MVP 阶段可以暂不开放 public。

## 11. 节点流中的知识库调用逻辑

知识库不应一次性全部塞给 AI，而应根据不同节点调用不同类型的内容。

### 11.1 意图解析节点

输入：

- 用户原始提示词；
- 当前 Space 信息；
- 可选的个人偏好。

输出：

- 主题；
- 主体；
- 情绪；
- 目标平台；
- 画面比例；
- 色彩倾向；
- 受众；
- 文案需求。

该节点主要理解用户需求，不建议大量注入知识库内容。

---

### 11.2 品牌知识匹配节点

输入：

- 意图解析结果；
- 当前 Space；
- 用户选择的知识库；
- 企业知识库规则；
- 团队知识库内容；
- 个人知识库内容。

输出：

- 推荐使用的 Logo；
- 推荐使用的标准色；
- 推荐参考图；
- 推荐产品图；
- 可用 Prompt 模板；
- 检测到的禁用规则。

该节点需要把检索出的内容展示给用户，由用户选择是否使用。

---

### 11.3 Prompt 专家节点

输入：

- 用户原始提示词；
- 意图解析结果；
- 用户选中的知识库素材；
- 品牌规则；
- Prompt 模板；
- 禁用规则。

输出：

- 专业绘图 Prompt；
- Negative Prompt；
- 推荐尺寸；
- 推荐风格；
- 推荐构图；
- 文本和 Logo 的放置建议。

该节点的输出应允许用户查看和轻度编辑。

---

### 11.4 图像生成节点

输入：

- 最终 Prompt；
- Negative Prompt；
- 选中的参考图；
- 模型参数；
- 图片比例。

输出：

- 底图；
- 生成参数；
- 模型调用记录。

---

### 11.5 排版与合成节点

输入：

- 底图；
- Logo；
- 标题文案；
- 副标题文案；
- 标准色；
- 字体规范；
- 布局模板。

输出：

- 合成后的图文成片；
- 图层信息；
- 文字位置；
- Logo 位置。

MVP 阶段建议使用模板化排版，而不是复杂自动排版。

---

### 11.6 自我评估节点

输入：

- 用户原始需求；
- 意图解析 JSON；
- 企业规则；
- 团队规则；
- 选中素材；
- 最终生成图。

输出：

- 综合评分；
- 分维度评分；
- 扣分项；
- 优化建议；
- 是否需要回溯重跑。

建议评分维度：

| 维度 | 说明 |
|---|---|
| 需求匹配度 | 是否符合用户最初需求 |
| 品牌一致性 | 是否符合企业/团队品牌规范 |
| 素材使用准确性 | 是否正确使用 Logo、产品图等素材 |
| 画面质量 | 是否存在畸形、模糊、构图混乱 |
| 文案与排版 | 文字是否清晰，排版是否合理 |
| 平台适配 | 是否符合目标平台尺寸和风格 |

规则建议：

```text
满分 10 分。
低于 6 分时，系统自动判断问题来源，并回溯到对应节点重新执行。
```

## 12. 团队知识库审核机制

团队和企业知识库建议支持审核流。

### 12.1 简单模式

适合小团队：

```text
成员上传 → 直接入库 → 可被节点流调用
```

### 12.2 审核模式

适合企业和正式团队：

```text
成员上传 → pending_review → 管理员审核 → active → 可被节点流调用
```

审核结果：

```text
通过：状态变为 active
拒绝：状态变为 rejected，并填写拒绝原因
```

## 13. 企业级策略配置

企业管理员应能配置企业级管控策略。

建议配置项：

| 配置项 | 说明 |
|---|---|
| 强制启用企业知识库 | 企业空间和团队空间生成时必须调用企业规则 |
| 禁止个人知识库参与企业项目 | 防止个人素材污染企业内容 |
| 团队知识库是否需要审核 | 控制团队上传内容是否需企业或团队管理员审核 |
| 成员作品默认归属企业 | 企业空间下生成的作品进入企业作品库 |
| 是否允许成员导出原图 | 控制普通成员导出权限 |
| 是否允许上传外部素材 | 降低版权风险 |
| 是否允许使用外部模型 | 防止企业数据泄露到未知模型 |

## 14. 推荐数据模型

### 14.1 KnowledgeBase

```ts
interface KnowledgeBase {
  id: string;
  name: string;
  description?: string;

  scope: 'personal' | 'team' | 'enterprise';

  ownerUserId?: string;
  teamId?: string;

  visibility: 'private' | 'team' | 'enterprise';

  itemCount: number;
  storageUsed: number;

  createdBy: string;
  createdAt: Date;
  updatedAt: Date;
}
```

### 14.2 KnowledgeItem

```ts
interface KnowledgeItem {
  id: string;
  knowledgeBaseId: string;

  type:
    | 'logo'
    | 'image_asset'
    | 'text_doc'
    | 'prompt_template'
    | 'negative_rule'
    | 'color_palette'
    | 'font_rule'
    | 'layout_template'
    | 'case_study'
    | 'bad_case';

  title: string;
  content?: string;
  fileUrl?: string;
  thumbnailUrl?: string;

  tags: string[];

  metadata: {
    colorHex?: string;
    fontName?: string;
    aspectRatio?: string;
    platform?: string;
    prompt?: string;
    negativePrompt?: string;
    source?: string;
  };

  visibility: 'private' | 'team' | 'enterprise';
  status: 'draft' | 'pending_review' | 'active' | 'rejected' | 'archived';

  createdBy: string;
  approvedBy?: string;
  rejectedReason?: string;

  createdAt: Date;
  updatedAt: Date;
}
```

```ts
interface EnterpriseMember {
```


## 15. 权限判断原则

后端在判断用户是否能访问某个知识库或知识项时，建议按以下顺序：

```text
1. 用户是否登录？
2. 用户是否是该知识库创建者？
3. 该知识库属于 personal / team / enterprise 哪个 scope？
4. 如果是 team，用户是否属于该团队？团队角色是什么？
5. 如果是 enterprise，用户是否属于该企业？企业角色是什么？
6. 当前知识项 visibility 是否允许用户访问？
7. 当前知识项 status 是否允许被调用？
8. 企业策略是否限制该操作？
```

示例：

```text
用户 A 想删除团队知识库中的素材 X：

1. A 是团队管理员：允许；
2. A 是知识库管理员：允许；
3. A 是创作者，且素材由 A 上传，并且团队允许创作者删除自己的素材：允许；
4. 其他情况：拒绝。
```

## 19. 研发实现注意事项

1. 不要把 `spaceId` 当成 `enterpriseId` 使用，Space、Team、Enterprise 应该是不同概念；
2. 知识库内容必须区分 `scope`、`visibility` 和 `status`；
3. 节点流只能默认调用 `active` 状态的知识项；
4. 企业规则优先级高于团队规则和个人偏好；
5. 团队知识库和企业知识库必须做权限校验；
6. 上传素材要预留对象存储字段，如 `fileUrl`、`thumbnailUrl`；
7. 文本资料和 Prompt 模板需要预留向量化状态字段；
8. 前端要把知识库选择做进节点流，不要只做成独立管理页面；
9. 知识库检索结果应展示给用户选择，不应完全黑盒注入 Prompt；
10. 权限相关逻辑必须由后端兜底，前端只做展示控制。

## 20. 总结

Brand-Flow 的知识库模块应被设计为：

> 个人可沉淀、团队可协作、企业可管控的多层级创作资产系统。

三层定位：

```text
个人知识库：自由创作，积累个人风格
团队知识库：共享素材，协同创作
企业知识库：统一品牌，强制管控
```

权限逻辑：

```text
企业角色决定企业级管理权
团队角色决定团队级协作权
知识库权限决定具体内容访问权
知识项状态决定是否能被 AI 调用
```

节点流调用逻辑：

```text
选择 Space
↓
选择知识库
↓
输入需求
↓
意图解析
↓
品牌知识匹配
↓
Prompt 专家
↓
图像生成
↓
排版合成
↓
自我评估
↓
保存作品 / 沉淀知识库
```

第一版的目标不是做一个复杂的企业知识管理系统，而是先打通：

```text
创建知识库 → 上传知识项 → 权限控制 → 节点流调用 → 生成结果 → 反向沉淀
```

只要这个闭环成立，Brand-Flow 的知识库就会成为项目区别于普通 AI 生图工具的核心竞争力。
